# معايير الكود وهندسة البرمجيات (Coding Standards)

**لماذا هذا الملف موجود؟**
لفرض معايير هندسية صارمة تضمن أن الكود الناتج نظيف، قابل للصيانة، وقابل للتوسع (Scalable).

## القواعد الأساسية:
1. **البرمجة كائنية التوجه (OOP):** التزام كامل بمبادئ التغليف (Encapsulation) واستخدام الـ Classes والـ Interfaces بدلاً من الـ Functions البسيطة حيثما أمكن.
2. **مبادئ SOLID:**
   - **S (Single Responsibility):** كل Class أو Function يجب أن يكون لها وظيفة واحدة فقط.
   - **O (Open/Closed):** الكود يجب أن يكون مفتوحاً للتمديد ومغلقاً للتعديل (استخدام Strategy Pattern لتنفيذ ذلك).
   - **L, I, D:** الالتزام بمبادئ ليفكوف، فصل الواجهات، وانعكاس التبعية.
3. **الأنماط التصميمية (Design Patterns):**
   - **Repository Pattern:** للتعامل مع قاعدة البيانات وتجريدها.
   - **Service Pattern:** لعزل منطق العمل (Business Logic) عن الـ Controllers.
   - **Strategy Pattern:** (هام جداً) لاستخدامه في:
      - مصادر جلب الأسعار (Data Sources).
      - معادلات التسعير المختلفة لكل شركة أو منتج.
4. **Clean Code:**
   - أسماء متغيرات ودوال واضحة ومعبرة.
   - دوال صغيرة (Small Functions) لا تتجاوز 20 سطراً.
   - تعليقات تشرح "لماذا" وليس "ماذا".

5. **اختبارات الوحدة (Unit Testing):**
   - الالتزام التام بكتابة اختبارات الوحدة (Unit Tests) لكل منطق عمل (Business Logic) جديد.
   - استخدام إطار العمل `Pest` المعتمد في المشروع.
   - لا يتم قبول أي Pull Request بدون تغطية اختبارية كافية (Test Coverage).

## المفاضلات (Trade-offs):
- تطبيق هذه الأنماط يزيد من عدد الملفات (Boilerplate) ولكنه يوفر سنوات من سهولة الصيانة.

## المخاطر (Risks):
- "الإفراط في الهندسة" (Over-engineering): تجنب تطبيق أنماط معقدة في أماكن لا تحتاجها.
